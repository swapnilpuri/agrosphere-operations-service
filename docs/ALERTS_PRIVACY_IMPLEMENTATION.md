## Generated-only modes and source flow

Both `operations.alerts.generated-test-mode` and `operations.alerts.privacy-generated-test-mode` default false. Privacy mode requires an exact nonempty generated-subject allowlist, rejects simultaneous legacy mode, and serves no actual-account rollout. No new default switches or private configuration files were added or changed. This implementation does not create recipients, modify roles/credentials or enable REAL data.

`AlertRuntime` retains the original legacy writer and delegates accepted incident revisions to `PrivacyAlertRuntime` only when the generated privacy mode is explicitly selected. Evaluation stays in the existing source transaction; there is no backfill/bootstrap/reconciliation writer or new broker event. `safeMode()` rejects every privacy request/source evaluation if any V6 alert table contains rows; a nonempty legacy environment needs a separate reviewed data plan. Legacy v1 routes return the closed 410 retirement problem in privacy mode and cannot bypass expiry. All new v2 routes remain authenticated, estate scoped, SIMULATED only and no-store.

The pure `PrivacyAlert` root contains no issuer/subject. Source versions, attention/version semantics and first shared acknowledgement retain AN rules. It records the true inactive transition, never incidental inactive edit time. Its expiry watermarks survive reopening and prevent read/history/attribution resurrection before physical cleanup. `PrivacyCommandRules` implements canonical UUIDv7, five-minute new-key admission, thirty-day hard key lifetime, earlier completion/copy expiry and pending-removal/cutoff checks. A previously admitted future-skew key is covered by request time + five minutes. Frozen old commands are never re-executed when receipts disappear.

## Persistence and maintenance

Additive `V7__alert_privacy_storage.sql` creates separate privacy root/read/attribution/evidence/receipt/removal tables, functions and new-object privileges. V1–V6 and every legacy table, row and grant are unchanged. Root JSON excludes actor identity and acknowledgement time; attribution resides only in expiring `privacy_ack`. History evidence stores no duplicate actor/private snapshot and joins retained attribution for protected queries. Successful command bodies are personal copies and expire/suppress with applicable read state, including across reopening. Removing one read marker is not claimed to erase other modules' source histories.

The runtime cannot DELETE, execute retention/removal functions, acquire DDL, or update acknowledgement/evidence/completed receipts. `privacy_cleanup(integer)` is an owner-controlled, non-HTTP SECURITY DEFINER routine with captured search path, PUBLIC execution revoked, database-clock cutoffs, 1–200 root batches and `FOR UPDATE SKIP LOCKED`. It deletes only eligible privacy rows, including expired-through watermarks after reopening. `privacy_request_removal(text,text)` requires an already verified operator request; it accepts no caller-supplied time, uses a short transaction-scoped identity advisory lock matching command admission, and is not a recipient/account API. No maintenance principal/role/credential was provisioned on an existing stack.

Cleanup is deliberately **not scheduled or enabled against the existing stack**. An authorized operating setup must arrange a daily protected job and overdue monitoring, plus specific maintenance execution authority. The routine itself is implemented and exercised only in disposable tests. Do not label the 24-hour physical-cleanup objective achieved in an unattended real environment merely because the function passes tests. A selected deployment must measure last successful run/oldest overdue work without logging personal row contents.

Read markers expire logically at INACTIVE + 30 days. Acknowledgement attribution/history expire at INACTIVE + 365 days. Unrelated edits do not move the clock. At the history deadline the operational acknowledgement remains true while attribution/time disappear; protected history returns explicit EXPIRED/empty state. Reopening returns PARTIAL for retained new history and never recovers old identities. Cleanup and logical suppression use the same root/watermark rules. Receipt copies have the earlier key/completion/read expiry; no identifying indefinite key tombstone is introduced.

Verified removal suppresses pre-cutoff personal read state and receipts, blocks new personal copies while pending, and cleans those copies while leaving acknowledgement/history on their separate policy. Completion adds a 66-day bounded ledger retention. Current authentication/estate/role checks always precede replay; no instantaneous identity-provider token revocation guarantee is inferred.

## Restore and operating controls

Keep restore targets isolated and all alert modes disabled until original deadlines and the independently preserved current removal ledger have been reconciled and eligible cleanup has run. The integration test makes a real custom-format PostgreSQL backup, removes live personal data, restores the earlier backup into a new isolated database, reapplies the newer removal ledger and cleans restored markers/receipts before any application can access them. It preserves the minimal root. This is generated recovery evidence, not a backup of the user's stack or an automatic production recovery service.

Ordinary logs 14 days, security logs 90 days, backups 35 days remain provisional operational limits. Log collectors, snapshots, incremental chains, replicas and exports must be inventoried/configured/tested in the selected environment. No external log rotation, provider retention rule or existing backup was configured here. Never claim in-process deadline arithmetic proves all-copy deletion. Keep protected recovery copies inaccessible to normal queries; normal backup removal can lag a live deadline by 24 hours plus 35 days. Failure/backlog handling must report the actual delay.

Maintain a current external deletion/removal ledger through the backup recovery window; do not overwrite it with an old database backup. Entries expire 66 days after completed live removal only when the bounded backup/key rules were enforced. If copy provenance or the current ledger is unavailable, do not enable restored alert access. Controller/contact, legal basis, final hosting/data flows and English/French notices remain unresolved real-account gates.
